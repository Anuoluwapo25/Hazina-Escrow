# Contract fuzzing runbook

How to run, extend and debug the property-based invariant suite for
`contracts/hazina-escrow`.

The _what_ lives in [`INVARIANTS.md`](INVARIANTS.md) — every invariant, its ID,
and the property that enforces it. This file is the _how_.

## Run it

```bash
cd contracts/hazina-escrow

cargo test                                        # gate: examples only, <1s
cargo test --features fuzz-tests --test fuzz      # invariant suite, ~7s
cargo test --features fuzz-tests                  # both
```

The fuzz target declares `required-features = ["fuzz-tests"]` in `Cargo.toml`,
so a plain `cargo test` does not compile it at all. The default gate stays a
sub-second pre-commit check.

### Case budget

`PROPTEST_CASES` overrides the per-property budget (default 48, set in
`tests/fuzz/harness.rs`):

```bash
PROPTEST_CASES=512  cargo test --features fuzz-tests --test fuzz   # ~100s
PROPTEST_CASES=4096 cargo test --features fuzz-tests --test fuzz   # deep run
```

Rough cost: one case builds an entire Soroban world (token contract, escrow
contract, initialize, mint), so wall-clock is close to linear in the budget.
47 properties × 512 cases ≈ 100 s on a CI runner.

### One property

```bash
cargo test --features fuzz-tests --test fuzz -- conservation::release_conserves
PROPTEST_CASES=10000 cargo test --features fuzz-tests --test fuzz -- fee_bounds::
```

## Layout

```
tests/fuzz/
  main.rs               target root; declares the modules
  harness.rs            World builder, strategies, expected-value model, config
  conservation.rs       I1–I4    value conservation          (#532, #533)
  settlement.rs         I5–I7    release XOR refund          (#534)
  fee_bounds.rs         I8–I11   fee bounds, min-1-stroop    (#535)
  lock_multi.rs         I12–I14  batch totals, ids, atomicity(#536)
  circuit_breakers.rs   I15–I17  amount + rate breakers      (#537)
  state_machine.rs      I18–I23  dispute, pause, access      (#538)
  fee_differential.rs   contract vs backend fee math         (#540)
tests/fixtures/
  fee_vectors.json      generated by the backend; see below
proptest-regressions/   committed failing seeds, one file per module
```

Everything goes through `harness::World`, which builds a world with a token,
an initialised contract, and a treasury distinct from the admin so "the
platform got paid" and "the admin got paid" are separable assertions.

Note `harness::bare_env()`: it disables Soroban's snapshot-at-drop. Snapshots
are worth committing for the example tests, but a property test builds one
`Env` per case, and leaving capture on dumps thousands of near-identical JSON
files into `test_snapshots/` on every run.

## When a property fails

1. **Read the minimal input.** proptest shrinks before reporting. The
   `minimal failing input:` line is usually the whole diagnosis.

2. **The seed is already saved.** proptest appends it to
   `proptest-regressions/<module>.txt` and replays it before any new case on
   every subsequent run.

3. **Commit the seed.** Same commit as the fix. That file is the permanent
   proof the bug is gone — a seed that only ever existed on a CI runner is a
   bug nobody can reproduce. The suite writes to a fixed directory rather than
   proptest's default source-parallel path precisely so these land somewhere
   predictable and get committed.

4. **Add the failing input as an example test too**, in `src/lib.rs::tests`, if
   the case is interesting on its own. The property proves the class; the
   example documents the specific bug and runs in the fast gate.

5. **Decide whether it is the contract or the property.** Both happen. A
   property encoding an assumption the contract never made is a bug in the
   test — fix the property and say so in the commit message. If the contract's
   real behaviour turns out to be surprising but intended, record it under
   "Known asymmetries" in `INVARIANTS.md` and pin it with a test, so it cannot
   change silently.

Reproduce a specific seed without waiting for the whole file:

```bash
PROPTEST_CASES=1 cargo test --features fuzz-tests --test fuzz -- <property_name>
```

## Adding a property

1. Add or amend the invariant in `INVARIANTS.md` first, with an ID. If you
   cannot state it in one sentence, it is more than one invariant.
2. Put the property in the module matching the invariant's section. Name it
   after what must hold, not after what it calls:
   `release_conserves_locked_value`, not `test_release_2`.
3. Reference the invariant ID in the doc comment, and the property name back in
   `INVARIANTS.md`. The cross-reference is what stops the doc rotting.
4. Take inputs from `harness`'s strategies rather than inventing ranges —
   they are derived from the contract's own constants, so they cannot drift
   away from the real boundaries.
5. Use `prop_assert!` / `prop_assert_eq!`, not `assert!`. Plain `assert!`
   aborts the case instead of letting proptest shrink it.
6. Assert on `World::balances().total()` in anything that moves money. A payout
   to some unaccounted address still satisfies per-account checks but breaks
   the sum.

## The fee vector fixture

`tests/fixtures/fee_vectors.json` is the contract between the Rust contract
math and the backend's `platformFee` / `sellerShare`. It is **generated, not
hand-written**:

```bash
npm run gen:fee-vectors --prefix backend
```

The generator (`backend/src/common/fee-vectors.ts`, with a thin CLI at
`backend/scripts/gen-fee-vectors.ts`) calls the real backend functions over a
fixed price grid, so the file is a record of what the backend actually does
rather than a transcription of it. `toFixed(4)` rounds ties away from zero and
Rust's formatter rounds to even, so a hand-port to Rust would be testing the
port; the fixture sidesteps that entirely.

Two tests guard it from opposite sides:

| Test                                                | Fails when                           |
| --------------------------------------------------- | ------------------------------------ |
| `backend/src/common/constants.differential.test.ts` | the fixture drifts from the backend  |
| `tests/fuzz/fee_differential.rs`                    | the contract drifts from the fixture |

If you change `PLATFORM_FEE_RATE` or either backend helper, regenerate and
commit the fixture in the same change.

**The measured divergence.** The backend quantises the fee to four decimals of
a whole token unit — 1 000 stroops — so its answer can sit up to 500 stroops
from the exact fee. The contract truncates, costing under one stroop. The
budget is therefore 501 stroops and is dominated entirely by the backend's
rounding, not by the contract's. Below ~0.001 units the backend reports a fee
of zero where the contract charges its 1-stroop minimum. Treat backend figures
as display values; the contract's integer result is authoritative.

## CI

`.github/workflows/contract-fuzz.yml`, three jobs:

| Job                | Runs                                        | Purpose                                     |
| ------------------ | ------------------------------------------- | ------------------------------------------- |
| `gate`             | `cargo test --locked`, release build        | Deterministic, no feature flag              |
| `fuzz`             | `cargo test --locked --features fuzz-tests` | `PROPTEST_CASES=512` on PRs, `4096` nightly |
| `fee-differential` | backend vitest                              | Fixture drift, from the JS side             |

The `fuzz` job uploads `proptest-regressions/` as an artifact and warns in the
job summary when a run generates a seed that is not already committed. Trigger
a deeper run by hand from the Actions tab; the `cases` input sets the budget.

## Known limits

- **`i128` overflow is out of scope.** The properties bound amounts to what the
  circuit breaker allows. `release_one` computes `amount * fee_bps` before
  dividing, which would overflow above roughly `i128::MAX / 2_000` — far above
  any reachable balance, and `overflow-checks = true` in the release profile
  turns it into a panic rather than a wrap.
- **Token contract behaviour is assumed.** Every property uses Soroban's
  Stellar-asset contract. A non-standard token that reverts or takes a transfer
  fee is not modelled.
- **Auth is mocked.** `mock_all_auths()` satisfies every `require_auth`, so the
  access-control properties exercise `assert_admin` and friends, not signature
  verification.
- **Multi-transaction ordering is not modelled.** Each case runs inside one
  test env; genuine concurrent submission against a live network is out of
  scope for a property suite.
